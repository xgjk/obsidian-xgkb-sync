# XGKB Sync 同步目标与重构基线

> 本文档是插件后续开发与重构的第一优先级约束。任何功能改动、Bug 修复、架构调整，都必须先对齐本文档目标，再进入实现阶段。

## 1. 插件目标（What）

XGKB Sync 的核心目标是：

1. 在 Obsidian 与玄关知识库之间实现**可预测、可恢复、可追踪**的文件同步。
2. 在 `push / pull / bidirectional` 三种方向下，保证文件内容与文件路径的最终一致性。
3. 在出现增量漏报、网络失败、部分操作失败时，保持幂等，可在后续同步轮次自动收敛。
4. 让同步行为可观测（可解释“为什么这样决策”），而不是黑盒执行。

## 2. 非目标（What Not）

以下不作为当前阶段必须达成目标：

1. 绝对最优性能（优先正确性，其次性能）。
2. 所有路径变化都必须用目录级 API 一次完成（目录聚合是优化，不是正确性前提）。
3. 单轮同步内消除所有历史不一致（允许多轮收敛，但每轮结果必须可解释）。

## 3. 同步正确性优先级（Priority）

从高到低：

1. **数据正确性**：内容不能丢、不能错覆盖。
2. **路径正确性**：移动/重命名结果正确，不能误移动其他文件。
3. **幂等与可恢复**：同一操作重试不产生额外副作用。
4. **可观测性**：日志可复盘计划与执行。
5. **性能优化**：并发、目录聚合、增量缩小范围等。

## 4. 强约束（Invariants）

后续实现必须满足：

1. 文件级计划永远是真相来源；目录级计划只能由文件级计划“可证明地”推导。
2. 任何 `from == to` 的 no-op 计划，不得进入执行阶段。
3. destructive 决策（删除、目录级 move）不能仅依赖增量线索，必须有确认条件。
4. 执行顺序固定：`路径变化（rename/move）` 在前，`内容更新` 在后。
5. pending 状态必须有完整生命周期：创建 -> 消费/ack -> 清理，禁止残留污染下一轮。

## 5. 重构方向（How）

采用“渐进重构”而非推倒重来：

1. 先拆分 `plan` 与 `apply`，保持行为不变。
2. 再将目录聚合下沉为优化器，不满足证明条件自动回退文件级。
3. 最后升级 pending 语义与回放能力（plan/result）。

## 6. 每轮改动的完成定义（Definition of Done）

每次改动必须同时满足：

1. `npm run build` 通过。
2. 最近改动文件 lint 无新增错误。
3. 关键回归场景通过（至少）：
   - 修改内容后移动文件；
   - 同一文件连续两次移动（A->B->C）；
   - 目录内部分文件移动（不得误聚合整目录）。
4. 日志中能看出“计划 -> 执行 -> 落库”的闭环，不出现不可解释行为。

## 7. 失败处理策略（Failure Policy）

当某方案首次失败时，不重复同一动作“再试一次”，必须：

1. 先确认当前已验证状态；
2. 只调整一个关键变量；
3. 明确下一步成功/失败信号；
4. 记录本次教训并同步到本文档或相关方案文档。
